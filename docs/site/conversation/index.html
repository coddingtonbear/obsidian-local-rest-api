How it works

An agent that can see what Obsidian sees

Most ways of getting an agent into a vault treat it as a directory of text. That works until the agent needs to know which notes carry a tag, what the note in front of you is, or how to change one section of a long file without rewriting the whole thing.

Because this server lives inside Obsidian, none of those are hard problems. It reads the metadata cache the app already maintains, it can name the file you currently have open, and it edits by address — a heading path, a block reference, a frontmatter key — rather than by rewriting bytes. Writes go through Obsidian's own vault API, so the app you are looking at never misses a change or overwrites one.

  • Read and writeAny file in the vault, including attachments — plus the note that happens to be open right now.
  • Edit by addressAppend under a heading, replace a block, set a frontmatter field. Optimistic concurrency stops two writers from stepping on each other.
  • Search properlyObsidian's own fuzzy search, or a structured JsonLogic query across frontmatter, tags, paths, and content.
  • Run the appList and execute any Obsidian command, and open a note on screen when a human should look at it.
  • Know the vaultEvery tag with its usage count; the heading, block, and frontmatter map of any file before touching it.

Why this one

Compared with pointing a filesystem server at the folder

A filesystem MCP server is genuinely simpler, and it keeps working when Obsidian is shut. What it cannot do is see any of the structure Obsidian builds on top of those files — or tell the running app that something changed.

  This plugin Filesystem MCP server Third-party REST wrapper
Tags, links, and frontmatter Obsidian's live metadata cache Re-parsed from the raw files Whatever this plugin returns
Changes reach the open app Immediately — written through Obsidian Written behind its back Whatever this plugin does
Editing one section By heading, block, or field Usually a whole-file rewrite Only what it chooses to expose
The note you have open Addressable directly Unknowable Only if it proxies it
Obsidian commands Listed and executable Out of reach Only if it proxies them
Extra software to run None beyond the plugin A separate server A separate server, plus this plugin
Works with Obsidian closed No Yes No

The last row is the trade-off, said plainly. Worth knowing too: the popular third-party Obsidian MCP servers are wrappers that call this plugin's REST API underneath — so if you are running one of those, you are already running this, with an extra process in between.

Not only for agents

The same vault, over plain HTTP

Long before MCP existed, this was a REST API — and it still is. Every capability an agent gets through a tool call is also an ordinary HTTP endpoint, documented in OpenAPI, reachable from a shell script, an iOS Shortcut, a browser extension, or anything else that can make a request. 

# Append a line under a heading. No JSON escaping required.
curl -k -X PATCH \
  -H "Authorization: Bearer $KEY" \
  -H "Operation: append" \
  -H "Content-Type: text/markdown" \
  --data "- One more thing" \
  https://127.0.0.1:27124/vault/Projects/API.md/heading/Log

The full reference is interactive: every route, parameter, and response shape, generated from the same specification the plugin serves to MCP clients at runtime.

Quick start

Three minutes, start to finish

Install the plugin from Obsidian's community browser, then open Settings → Local REST API and copy your API key.

Claude Code

claude mcp add --transport http obsidian https://127.0.0.1:27124/mcp/ \
  --header "Authorization: Bearer <your-api-key>"

Cursor · ~/.cursor/mcp.json

{
  "mcpServers": {
    "obsidian": {
      "url": "https://127.0.0.1:27124/mcp/",
      "headers": { "Authorization": "Bearer <your-api-key>" }
    }
  }
}

Claude Desktop · via mcp-remote

{
  "mcpServers": {
    "obsidian": {
      "command": "npx",
      "args": [
        "mcp-remote@latest",
        "https://127.0.0.1:27124/mcp/",
        "--header",
        "Authorization: Bearer <your-api-key>"
      ]
    }
  }
}

Any client that speaks the Streamable HTTP transport works the same way: that URL, that header.

Trust

Your notes stay on your machine

This is a local server, not a service. There is no account, no telemetry, and no upstream — the only things that reach your vault are the clients you hand a key to.

Loopback by default

The server binds to 127.0.0.1. Nothing on your network can reach it unless you deliberately change that.

Authenticated everywhere

Every route but the status check requires your bearer API key, over HTTPS with a certificate generated on your machine.

Open source

MIT licensed, developed in the open, and reviewed by the Obsidian community plugin process.

Questions

Before you install

Does Obsidian have to be open?

Yes — and that is what makes the difference. The metadata cache, the active file, Obsidian's search, and the command palette all live inside a running app. If you specifically want vault access while Obsidian is closed, a filesystem tool is the better fit.

Do I still need a third-party Obsidian MCP server?

No. The MCP server is built into the plugin, so there is no bridge process to install, configure, or keep up to date — and the popular third-party servers are wrappers around this plugin's REST API anyway.

What about the certificate warning?

The certificate is self-signed because it is issued locally for a loopback address. Trust it from https://127.0.0.1:27124/obsidian-local-rest-api.crt, hand it to your client directly, or enable the optional plain-HTTP port for clients that cannot be talked round.

Can an agent destroy my notes?

It has the access you grant it, so treat the API key as you would any other credential — and keep your vault in version control or a backup, as you would anyway. Deletes move files to the trash by default, section edits touch only the section they name, and an ifMatch token lets a careful client refuse to write over a file that changed underneath it.

Does it work on mobile?

No, desktop only. The plugin needs Node's TLS and HTTP server APIs, which Obsidian's mobile runtime does not provide.

Can my own plugin add to the API?

Yes. Plugins can register their own authenticated routes and MCP tools on this server, and a published, generated type package means the whole host surface is checked at compile time.
