Capabilities

        
Everything is a request. Everything comes back.

        

          The same capabilities are exposed twice — as HTTP endpoints for anything that can make a
          request, and as MCP tools for anything that speaks to a model. Learn one, and you know
          the other.
        

      


      

        

          
Read and write any file

          
Full CRUD across the vault, including binary attachments, directory listings, and the note that happens to be open in front of you.

          
GET /vault/notes/daily.md
200 — text/markdown

        


        

          
Edit one section, not the file

          
Target a heading, block reference, or frontmatter key and append, prepend, replace, delete, or move just that part. The rest of the note is never rewritten.

          
PATCH /vault/daily.md
{"targetType":"heading","operation":"append"}
200 — section updated

        


        

          
Search the way Obsidian does

          
Obsidian's own fuzzy search with scored snippets, or a JsonLogic expression evaluated against every note's frontmatter, tags, path, and content.

          
POST /search/
{"in": ["reading", {"var": "tags"}]}
200 — matching notes

        


        

          
Drive the app, not just the files

          
List and execute any Obsidian command exactly as the command palette would, open a note in the UI, or read every tag in the vault with its usage count.

          
POST /commands/graph:open/
204 — executed in Obsidian

        


        

          
Connect an agent in one line

          
A Streamable HTTP MCP server at /mcp/ with sixteen tools covering the vault, search, the active file, and the command palette.

          
POST /mcp/
tools — vault_patch, search_query, …

        


        

          
Extend it from your own plugin

          
Other plugins register authenticated routes and MCP tools against this server. Install the typed package and the whole surface is checked at compile time.

          
npm i -D obsidian-local-rest-api
ts — getAPI(app, manifest, 2)

        

      

    

  


  

    

      

        
Surgical edits

        
Append a line to a heading without touching the note around it.

        

          Send an instruction — an operation, a scope, and a target — and the API applies it to
          exactly that node. Heading levels in your content are rebased for you, whitespace is
          handled for you, and an ifMatch token makes the edit conditional on the file
          being unchanged since you read it.
        

      


      

        

          
The instruction


{
  "targetType": "heading",
  "target": ["Log"],
  "operation": "append",
  "content": "- Shipped the release"
}

          
Or, with nothing to escape


# Target in the URL, operation in a header,
# body is the raw payload.
curl -k -X PATCH \
  -H "Operation: append" \
  -H "Content-Type: text/markdown" \
  --data "- Shipped the release" \
  .../vault/daily.md/heading/Log

        

        

          
daily.md — after


---
status: open
---

# Daily

## Notes

Nothing here changed.

## Log

- Reviewed the queue
- Shipped the release

## Tomorrow

Also untouched.

        

      

    

  


  

    

      

        
Compared with the alternatives

        
The difference is that it runs inside Obsidian.

        

          A server that reads your vault off disk sees a folder of text files. This one sees what
          Obsidian sees: the resolved metadata cache, the active file, the command palette — and it
          writes back through Obsidian's own vault API, so the running app never misses or clobbers
          a change.

Quick start

        
Install, copy the key, make a request.

        

          Enable the plugin and open Settings → Local REST API for your API key.
          Everything below uses it as a bearer token.
        

      


      

        
        
        
        
      


      

        


# Read a note
curl -k -H "Authorization: Bearer <your-api-key>" \
  https://127.0.0.1:27124/vault/path/to/note.md

# Append a line under a heading — no JSON escaping needed
curl -k -X PATCH \
  -H "Authorization: Bearer <your-api-key>" \
  -H "Operation: append" \
  -H "Content-Type: text/markdown" \
  --data "- One more thing" \
  https://127.0.0.1:27124/vault/notes/daily.md/heading/Log

        


        


claude mcp add --transport http obsidian https://127.0.0.1:27124/mcp/ \
  --header "Authorization: Bearer <your-api-key>"

        


        


// claude_desktop_config.json
{
  "mcpServers": {
    "obsidian": {
      "command": "npx",
      "args": [
        "mcp-remote@latest",
        "https://127.0.0.1:27124/mcp/",
        "--header",
        "Authorization: Bearer <your-api-key>"
      ]
    }
  }
}

        


        


// ~/.cursor/mcp.json
{
  "mcpServers": {
    "obsidian": {
      "url": "https://127.0.0.1:27124/mcp/",
      "headers": {
        "Authorization": "Bearer <your-api-key>"
      }
    }
  }
}

Questions

        
Before you install

        

          

            Does Obsidian have to be running?
            
Yes — and that is the point. Running inside Obsidian is what gives the API the live metadata cache, the active file, and the command palette. If you need vault access with the app closed, a filesystem tool is a better fit.

          

          

            How exposed is this?
            
The server binds to 127.0.0.1 by default and every route but the status check requires a bearer API key. HTTPS uses a certificate generated on your machine; the plain-HTTP port is off unless you turn it on.

          

          

            Do I still need a third-party MCP server?
            
No. Several exist, and the popular ones are wrappers that call this plugin's REST API anyway. The MCP server is built in, so there is nothing extra to install or keep running.

          

          

            What about the certificate warning?
            
Trust the certificate from https://127.0.0.1:27124/obsidian-local-rest-api.crt, point your client at it directly, or enable the plain-HTTP port for clients that cannot be persuaded.

          

          

            Mobile?
            
Desktop only. The plugin needs Node's TLS and HTTP server APIs, which Obsidian's mobile runtime does not provide.

          

        

      


      

        
Extensions

        
Other plugins build on it

        

          A plugin can register its own authenticated routes, public routes, and MCP tools on this
          server — so a capability that belongs to your plugin ships with your plugin, and every
          client that already has an API key can reach it.
        

        


// your plugin
import { getAPI } from "obsidian-local-rest-api";

const api = getAPI(this.app, this.manifest, 2);

api?.addRoute("/my-plugin/thing")
   .get((req, res) => res.json({ ok: true }));

        

        

          The published types are generated from the plugin's own source, so they cannot drift from
          what the host actually offers.
